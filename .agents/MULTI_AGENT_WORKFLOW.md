本仓库采用**多模型角色分工 + 强制交叉验证**的开发协作模式，所有参与本项目的 Agent 均须同时遵守根目录 [AGENTS.md](../AGENTS.md) 中的 T3 Code 工程规范与本文档的协作流程。

## 2. 协作铁律

1. **方案独立，实现独占**：方案阶段 Gemini 4 Neon 与 Claude Opus 5.5 必须各自独立思考、互不可见、均不得改动项目文件；方案确认进入开发后，**仅由 Gemini 4 Neon 独占写代码**，杜绝多模型并发改同一批文件造成踩踏。
2. **顾问只解难点，不干主力活**：Claude Opus 5.5 除方案阶段独立出方案外，在开发阶段不承担常规 CRUD、页面堆砌、普通重构或琐碎修复；只有在面临深度技术难点或主控受阻时才向其定向咨询。
3. **验收者不能是作者**：主控不得自写自签。所有代码审查、测试评估与验收均由未参与编码的 GPT-6.2-sol 独立执行。
4. **融合必须逐维度对照**：方案汇报必须向用户同时呈现方案 A、方案 B、逐维度对照融合稿及「待用户拍板项」，不能只给一段笼统总结；**用户确认方案前，绝不提前动手改代码**。
5. **每次复审开新委派**：针对 GPT-6.2-sol 的每一轮代码审查或修复后复检，都必须新建一次 `delegate_task`（在 `clientRequestId` 中体现轮次，如 `<topic>-review-round2`），不要沿用旧对话通过 `t3_thread_send` 续聊。
6. **只读边界写入 Brief**：派发给 Claude Opus 5.5 和 GPT-6.2-sol 的每个 `delegate_task` 都必须显式注明「仅输出方案/分析/审查报告，不要创建或修改任何项目文件」。
7. **异常透明，不静默降级**：若目标模型或 Provider 不可用、报错或超时，必须直接向用户说明真实报错并等待指令，不私自换模型、不伪造已通过的审查结论。
8. **叠加遵守 T3 Code 工程基线**：方案设计、编码与审查必须共同覆盖 [AGENTS.md](../AGENTS.md) 中的三条红线、Hit every surface（入口/多端/Provider/MCP/契约/逆向状态/连接模式/i18n/文档）、Effect 服务规范、性能约束及验证要求。

## 3. 标准端到端工作流

### 阶段 1：独立双方案 → 互补择优 → 用户确认

1. **事实核实（主控）**：收到用户需求后，Gemini 4 Neon 先快速调研仓库，确认相关代码路径、现有架构、约束条件与受影响范围，形成统一的「已核实事实基线」。
2. **并行独立出方案**：
   - 主控通过 `delegate_task`（`mode: "async"`）将需求原话与事实基线发给 **Claude Opus 5.5**，要求其独立产出完整方案 B（只读，不改文件）。
   - 同时，**Gemini 4 Neon** 独立产出完整方案 A（不等待或照搬 Claude 结论）。
3. **互补择优融合（主控）**：两份独立方案齐备后，按固定结构向用户呈现：
   - **一、方案 A（Gemini 4 Neon）**：核心思路、优势/亮点、风险与改动面。
   - **二、方案 B（Claude Opus 5.5）**：核心思路、优势/亮点、风险与改动面。
   - **三、互补择优融合稿**：
     - 逐维度对照表（`维度 | 方案 A | 方案 B | 采纳 | 理由`）；
     - 「双方都遗漏但必须补齐的项」（重点核对 T3 Code 多端/多入口、契约、性能、测试与逆向状态）；
     - 落地实施步骤与验证计划。
   - **四、待用户拍板项**：明确列出存在权衡的分叉决策及各选项代价。
4. **用户拍板**：等待用户确认最终方案；确认前保持工作区代码干净。

### 阶段 2：主控独占实现（按需咨询 Claude 难点顾问）

1. **主力实现**：Gemini 4 Neon 严格按照用户确认的融合方案编写代码、补充测试并跑通本地验证（`vp test run`、`vp run typecheck`、必要时的实机/浏览器集成检查，提交或推送前跑 `vp run check:changed`）。
2. **触发 Claude Opus 5.5 难点咨询的条件**（满足任一即可触发）：
   - 遇到复杂架构设计、并发/状态同步、底层协议、性能瓶颈或跨层疑难问题；
   - 主控针对同一技术卡点**连续尝试 2 轮**仍未根本解决；
   - 实施中暴露出方案未预见的深层约束，需要第二架构视角评估取舍。
3. **难点咨询方式**：只发送聚焦的现状、关键代码路径及已失败的尝试现象，向 Claude 获取根因判断与 2~3 个候选解法的具体代码/参数要点；由主控验证并落地，Claude 不直接改文件。

### 阶段 3：独立代码审查、测试与验收（GPT-6.2-sol）

主控完成实现并自检通过后，发起新的 `delegate_task` 交由 **GPT-6.2-sol** 独立验收：

- **代码审查**：逻辑正确性、边界与异常路径、类型安全与 Effect/React 规范、性能/安全风险、是否完整满足确认方案及 `AGENTS.md` 中的多端覆盖要求。
- **测试审查**：检查新增与现有测试是否真正覆盖核心逻辑和回归场景，可运行相关只读测试/检查命令交叉核验，指出缺失的测试用例。
- **功能/视觉验收**：核验改动是否满足用户原始需求；如涉及前端/移动端视觉变动，结合主控提供的截图使用看图能力逐项验收。
- **统一输出格式**：
  - 按 **P0（阻断必须修）/ P1（重要应当修）/ P2（优化建议）** 分级列出问题；
  - 每条必须精确到**文件路径、行号、问题根因、复现/触发条件、修复建议**；
  - 给出明确验收结论：`通过` / `修复后复检` / `打回重做`。

### 阶段 4：闭环修复与复检签收

1. 主控逐条核查 GPT-6.2-sol 的审查结论：对真实缺陷立即修复并补齐测试；若存在基于误解的误报，需列出源码证据说明理由。
2. 所有 P0 与有效 P1 修复完成并重跑验证后，向 GPT-6.2-sol 发起**新一轮 `delegate_task`** 复检（附带本轮修复 diff 范围、上轮问题清单与逐项处置说明）。
3. 直到无遗留 P0/P1、验收通过后，由主控向用户汇报最终交付物、验证结果及审查签收摘要。

## 4. 委派 Brief 标准模板（五段式）

每次调用 `delegate_task` 须包含五要素：**角色 / 背景与已核实事实 / 交付物与格式 / 禁止事项 / 验收口径**，并设置语义化 `clientRequestId`。

### 4.1 独立方案 Brief（→ Claude Opus 5.5）

- Target: `providerInstanceId: "antigravity"`, `model: "claude-opus-5-5"`, `options: { thought_level: "high" }`
- `clientRequestId`: `<topic>-claude-plan-v1`

```text
【角色】请作为独立架构师，针对以下需求给出完整、可落地的技术方案。
【背景与已核实事实】
- 仓库路径：/Users/weimu/Documents/T3project/t3code
- 用户原始需求：<原话>
- 已核实的代码现状与关键文件：<文件路径与现状摘要>
- 本方案将与主控（Gemini 4 Neon）的独立方案逐维度对比、互补择优，最终提交用户拍板。
【交付物与格式】
请用中文输出结构化方案，覆盖：
1. 核心架构设计与数据/控制流
2. 涉及模块、契约与文件改动清单（含 Web/Desktop/Mobile/Server 多端考量）
3. 关键边界条件、性能与安全风险及应对
4. 测试与验证策略
5. 实施步骤与关键权衡点（供用户决策）
【禁止事项】仅做只读调研并输出方案，严禁创建、修改或删除任何项目文件，严禁执行有副作用的命令。
【验收口径】方案须基于实际代码核实（引用真实文件路径与符号），无空泛套话，细节可直接指导编码。
```

### 4.2 技术难点咨询 Brief（→ Claude Opus 5.5）

- Target: `providerInstanceId: "antigravity"`, `model: "claude-opus-5-5"`, `options: { thought_level: "high" }`
- `clientRequestId`: `<topic>-claude-consult-<n>`

```text
【角色】请作为技术难点顾问，针对以下单一卡点给出精准根因分析与解法（不负责主力开发）。
【背景与已核实事实】
- 卡点描述：<具体现象/报错/约束>
- 关键文件路径与上下文：<路径与行号>
- 已尝试过但失败的方案及现象：
  1. <做法> → <现象>
  2. <做法> → <现象>
【交付物与格式】输出：1) 根因判断；2) 2~3 个按成本排序的候选解法及取舍；3) 推荐解法的具体代码/参数要点；4) 验证有效的判定方法。
【禁止事项】只读查阅与建议，不要修改任何项目文件。
【验收口径】结论须对应真实源码事实，推荐解法具体到文件与关键逻辑改动点。
```

```text

【背景与已核实事实】
- 用户原始需求与已确认的融合方案摘要：<摘要>
- 本轮改动文件清单 / git diff 范围：<文件列表或 diff 获取方式>
- 主控已运行的本地验证结果：<命令与结果>
- （若为第 2+ 轮复检）上轮 P0/P1 问题清单及主控声称的修复方式：<清单>
【交付物与格式】
请按以下结构输出中文验收报告：
1. 总体结论（通过 / 修复后复检 / 打回重做）
2. 缺陷清单（按 P0 / P1 / P2 分级，每条注明文件:行号、问题说明、触发条件、修改建议）

【禁止事项】严禁修改、创建或删除任何项目文件；仅做代码阅读、只读命令验证与报告输出。
【验收口径】所有指出的问题必须经源码核实（标注真实路径与行号），复检轮次须逐项验证上轮 P0/P1 是否真正闭合。
```
