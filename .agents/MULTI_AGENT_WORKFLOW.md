## 2. 协作铁律

1. **GPT 严禁使用 fast 模式**：派发给 GPT-6.2-sol 的所有任务一律使用普通模式（不传 `fastMode: true` 或 `serviceTier: "fast"`），确保质量稳定。
2. **串行写入，杜绝踩踏**：当委派 GPT-6.2-sol 修改和优化代码期间，主控不得并发修改同一工作区文件；等待 GPT 完成后，由主控统一审查 diff、运行验证并验收。
3. **主控自主审查 → GPT 修改优化 → 主控验收**：
   - 先由 **Gemini 4 Neon** 对当前代码做全面自主审查（覆盖正确性、安全边界、性能、多端一致性、测试缺口与体验细节），输出精确到 `文件:行号` 的分级清单（P0/P1/P2）。
   - 再通过 `delegate_task` 将审查清单交给 **GPT-6.2-sol（普通模式）** 直接执行修改、优化和补齐回归测试。
   - 最后由 **Gemini 4 Neon** 独立审阅全部 `git diff`、核对每条清单闭合情况、执行完整验证（`i18n:check`、`check:changed`、必要时浏览器/端到端检查）并做出最终验收签收。
4. **每次迭代开新委派**：针对 GPT-6.2-sol 的每一轮修改优化任务，新建语义化 `clientRequestId` 的 `delegate_task`（如 `<topic>-gpt-optimize-round<N>`）。
5. **异常透明，不静默降级**：若目标模型或 Provider 不可用、报错或超时，必须直接向用户说明真实报错并等待指令，不私自换模型、不伪造验收结论。
6. **叠加遵守 T3 Code 工程基线**：编码、优化与验收必须共同覆盖 [AGENTS.md](../AGENTS.md) 中的三条红线、Hit every surface（入口/多端/Provider/MCP/契约/逆向状态/连接模式/i18n/文档）、Effect 服务规范、性能约束及验证要求。

## 3. 标准迭代闭环

1. **阶段性验收（仅本轮一次性由 Claude Opus 5.5 只读验收；后续常规迭代不再调用 Claude 审查，Claude 恢复仅在深层难点时提供定向方案指导）**。
2. **主控自主审查与审核（Gemini 4 Neon）**：逐模块审阅改动与存量边界，定位 P0/P1/P2 问题、冗余复杂度、性能隐患与测试空白；或整理验收反馈为精确到 `文件:行号` 的修复清单。
3. **委派修改优化（→ GPT-6.2-sol，普通模式，严禁 fast 模式）**：通过五段式 Brief 明确范围、目标、禁止事项与验证要求，由 GPT 直接落地修改、优化与回归测试补齐。
4. **主控独立审核与验收（Gemini 4 Neon）**：
   - 逐行审核 GPT 的改动 diff，验证没有引入回归或越界改动；
   - 运行 `vp run i18n:check`、`env -u T3CODE_PORT vp run check:changed` 及针对性回归测试；
   - 若仍有残留问题，继续派发 GPT 定向修复并审核，直到完全达成计划目标后提交并向用户汇报。
